# Identity and access management

## Architecture and scope

`app/models/user.py` defines the SQLAlchemy 2.0 user and `UserRole` enum. UUIDs are
generated by the application. All fields are non-null, the email has a unique
B-tree index, and canonical lowercase email storage is enforced by a database
check. Login normalizes whitespace and case. Future identity creation paths must
validate emails and store that same canonical form.

Roles use a VARCHAR plus a named CHECK constraint, rather than a PostgreSQL enum
type. Adding INSTRUCTOR or MODERATOR requires extending `UserRole` and an explicit
migration replacing the CHECK constraint. MEMBER is the least-privilege default.
UTC-aware timestamps have database defaults. SQLAlchemy updates `updated_at` on
ORM updates, and the PostgreSQL migration adds a trigger for updates from any
database writer.

The repository contains only identity lookups. `AuthService` owns password
verification, token issuance, token validation, and identity resolution. Routers
translate the HTTP contract, and dependencies connect the request-scoped async
session to the service. No user CRUD, registration, or default administrator is
provided. Login requires an existing, securely provisioned identity; production
users are never seeded by startup or the migration.

## Configuration

Add these keys to `.env` or inject them through the deployment environment:

| Variable | Default | Validation |
| --- | --- | --- |
| `JWT_SECRET_KEY` | Required; no default | Minimum 32/48/64 UTF-8 bytes for HS256/384/512; use cryptographically random material |
| `JWT_ALGORITHM` | `HS256` | HS256, HS384, or HS512 only |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `15` | 1–60 minutes |
| `REFRESH_TOKEN_EXPIRE_DAYS` | `7` | 1–90 days |
| `PLAYBACK_TOKEN_EXPIRE_MINUTES` | `30` | 1–240 minutes |

Generate a fresh secret locally and place it in `.env` or your secret manager;
do not commit it or include it in logs:

```powershell
.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(64))"
```

All workers must share the same secret. Rotating it invalidates outstanding tokens.
Settings mask the key in repr, serialization, and validation errors. Tests inject
a dedicated test-only key and never depend on real deployment credentials.

## Authentication flow

1. `POST /api/v1/auth/login` accepts JSON with `email` and `password`.
2. The repository finds the canonical email using the index.
3. The service verifies Argon2id and checks `is_active`. Unknown email, incorrect
   password, and inactive identity return the same HTTP 401 and Bearer challenge.
4. An active identity receives `access_token`, `refresh_token`, and
   `token_type: "bearer"`. The response is marked `Cache-Control: no-store`.
5. `GET /api/v1/auth/me` requires `Authorization: Bearer <access_token>`.
   The service verifies the signature, configured algorithm, expiry, not-before,
   issued-at, UUID subject, UUID token identifier, role, and access-token type.

   A third kind exists for media only: a **playback token** (`token_type:
   "playback"`) additionally carries a `lesson_id` and authorizes streaming one
   lesson's video for minutes. It is issued by the lesson resource endpoint, not
   by login, and is rejected by every bearer-authenticated route because those
   require the access type. Conversely an access or refresh token is rejected as
   a playback token. See `docs/storage.md` for the playback flow.
6. The dependency reloads the identity and rejects missing/inactive users. The
   response contains profile fields and timestamps, never the password hash.

## Refreshing an access token

`POST /api/v1/auth/refresh` renews a short-lived access token without asking for
credentials again. It is the only endpoint that consumes a refresh token.

Request — the token is the whole credential, so no `Authorization` header is
used or read; unknown fields are rejected:

```json
{ "refresh_token": "<token from login>" }
```

Response, marked `Cache-Control: no-store` and `Pragma: no-cache`:

```json
{ "access_token": "<new token>", "token_type": "bearer" }
```

Validation reuses the same decoding path as every other token — configured
signing key, algorithm allowlist, expiry, not-before, issued-at, and the
required `sub`, `role`, `token_type`, `jti`, `iat`, `nbf`, `exp` claims — and
additionally requires `token_type == "refresh"`. An access token, a playback
token, an unsigned (`alg: none`) token, or one signed with another key is
rejected. There is no second JWT implementation.

**The identity is reloaded from PostgreSQL; the token is not trusted for it.**
After the signature checks, the service loads the user by `sub` through the
existing repository and requires that it still exists and is still active. The
new access token is then signed with the **current database role**, never the
`role` claim carried by the refresh token. So:

- a deactivated account cannot refresh, from the next call onward;
- a deleted account cannot refresh;
- a promotion to ADMIN takes effect on the next refresh;
- a demotion to MEMBER takes effect on the next refresh;
- a tampered `role` claim grants nothing, because it is never read back.

Expiry and rotation: the refresh token is **not** rotated and its lifetime is
**not** extended, so a session ends exactly when the original refresh token
reaches `REFRESH_TOKEN_EXPIRE_DAYS`. An expired refresh token returns 401 and the
member logs in again. The flow is entirely stateless — no refresh-token table, no
revocation list, no server-side session — which is a deliberate trade recorded
under *Security decisions and limits* below.

Errors follow the existing conventions: a structurally invalid body (absent,
empty, wrong-typed or unknown fields) is a 422 validation error, and every
authentication failure is a 401 carrying the generic
`{"detail": "Invalid authentication credentials"}`. Nothing distinguishes an
unknown subject from a deactivated one, so the endpoint cannot be used to probe
which accounts exist.

For future routes, use `CurrentUser` for authentication or
`Depends(require_role(UserRole.ADMIN))` for authorization. Multiple supplied roles
are an allowlist; an empty allowlist denies everyone. Authorization uses the live
database role, so promotions, demotions, and deactivation apply immediately even
to previously issued access tokens. Authenticated users with an insufficient role
receive HTTP 403.

## Security decisions and limits

- Refresh is stateless: a refresh token stays valid until it expires and cannot
  be revoked individually. A compromised refresh token is therefore usable for up
  to `REFRESH_TOKEN_EXPIRE_DAYS`. Mitigations available today are deactivating the
  account (which blocks refresh immediately, since the identity is reloaded on
  every call) or rotating `JWT_SECRET_KEY`, which invalidates every outstanding
  token. Per-token revocation would require server-side token state and is not
  implemented.

- Passwords use Argon2id with the RFC 9106 low-memory profile (64 MiB, three
  iterations, four lanes) and independent random salts. See the
  [argon2-cffi API](https://argon2-cffi.readthedocs.io/en/25.1.0/api.html).
  Verification runs in worker threads with at most two concurrent jobs per app
  worker. Missing users still perform a dummy verification. Malformed hashes
  fail closed. Login passwords are bounded to 1,024 characters.
- JWT validation pins the configured algorithm and requires all identity and
  lifetime claims, following the [PyJWT API](https://pyjwt.readthedocs.io/en/stable/api.html).
  Tokens contain no email, names, or password hashes. JWT payloads are signed,
  not encrypted. Each token gets an independent random `jti`.
- Access and refresh tokens carry different types. A refresh token cannot call
  `/me` or satisfy role checks. This ticket implements issuance only: there is no
  refresh exchange, logout, rotation, revocation store, or reuse detection. Before
  enabling renewal, add persisted hashed refresh identifiers, atomic single-use
  rotation, expiry/revocation checks, and token-family reuse detection. A `jti`
  alone does not provide revocation. Access tokens currently last until expiry,
  user deactivation/deletion, or signing-key rotation.
- Clients must use HTTPS and protected token storage. For browser integration,
  introduce an HttpOnly/Secure refresh-cookie or BFF design with appropriate CSRF
  protection; do not persist refresh tokens in browser localStorage. The current
  API returns tokens in JSON as requested and does not set cookies.
- The password concurrency bound controls per-worker hashing memory; it is not
  a brute-force defense. Deployment must enforce distributed login rate limits
  by source and account at the gateway or a shared limiter before public exposure.
  Request bodies and Authorization headers must not be logged by the ingress.

## Migration and tests

Install dependencies, configure the JWT secret, then preview and apply the
already-created migration (application startup never changes the schema):

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m alembic upgrade head --sql
.\.venv\Scripts\python.exe -m alembic upgrade head
```

For a future schema change, create a migration against an up-to-date development
database; do not run this to duplicate the committed users migration:

```powershell
.\.venv\Scripts\python.exe -m alembic revision --autogenerate -m "Describe identity schema change"
```

Tests require no PostgreSQL instance and do not modify your configured database:

```powershell
.\.venv\Scripts\python.exe -m pytest app/tests/test_auth.py -q
.\.venv\Scripts\python.exe -m pytest -q
```

Coverage includes salted password hashing, login success/failure, profile field
filtering, inactive users, missing/malformed/expired/future tokens, missing claims,
wrong signatures/algorithms, refresh-token rejection, current database roles,
email constraints, settings validation, and offline PostgreSQL migration SQL.
SQLite tests exercise real async queries but cannot validate PostgreSQL trigger
execution. The existing optional `TEST_DATABASE_URL` integration check only tests
connectivity; it does not apply migrations or provision users.
